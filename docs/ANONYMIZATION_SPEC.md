# Anonymization Spec — Published App (publishProfile)

Binding rules for transforming `tools/league-data/raw/league_raw_2026.json`
(real names, real stat lines — NEVER ships) into the bundled
`league_2026_publish.json`. Goal: **break the identifiability stack** (right of
publicity / NIL risk, see `REALISTIC_LEAGUE_PLAN.md` legal section) while
preserving team-level realism. The lesson of Keller/Davis v. EA: a player can
be legally "identifiable" with no name at all — number + position + bio +
stats sufficed. So the unit of protection is the **combination**, not the name.

## 0. The identifiability stack (what makes a fake player "be" a real one)

| Strength | Identifier | publishProfile action |
|---|---|---|
| STRONG | Real or sound-alike name | REPLACE (independent fictional name) |
| STRONG | Exact career stat lines | NEVER SHIPPED (OVR arcs instead) |
| STRONG | Exact draft slot (year+round+pick) | Fuzz pick within round |
| STRONG | Real college + draft year combo | Swap college (same tier) |
| MEDIUM | Height/weight exact | Jitter |
| MEDIUM | Age + yearsPro exact | Age ±1 (balanced) |
| WEAK | Team + position + role tier | KEEP (this is the realism we want) |
| WEAK | Ratings profile (accurate QB etc.) | KEEP (our editorial model) |
| WEAK | Team strength / records / picks | KEEP (facts, aggregates) |

Rule of thumb: every STRONG identifier must be transformed; a player may keep
at most the WEAK rows intact. Team-level truth stays; individual-level truth
gets fuzzed.

## 1. Names — fully fictional, NOT sound-alike

- Generate from the game's existing name pools (`RandomNameGenerator`),
  **independently of the real name** — no derivation, no initial-preservation,
  no rhythm-matching. (Sound-alike names like "Garret Joff" are the DEV profile
  only; they demonstrate intent to evoke the persona and are the worst option
  legally in a shipped product.)
- Deterministic: seeded per player with `seed = SHA256(globalSeed + realName +
  team + pos)` so rebuilds are stable.
- Collision guards (hard failures in the QA gate):
  1. Levenshtein distance ≥ 3 to EVERY name in the real-players blocklist
     (all players in the raw data + a bundled list of notable NFL names of the
     last ~15 years).
  2. Not identical to any other generated player/coach name in the league.
  3. Same-initials + same-team + same-position as the real counterpart is
     forbidden (regenerate on hit) — initials are a recognition shortcut.
  4. **Recombination.** Guard 1 binds the CROSS PRODUCT, not just the pairs a
     tool emits. Anything that draws a given name and a surname independently
     from two pools can reach every combination of them: the app's
     `RandomNameGenerator` / owner / coach pools, and the runtime
     support-staff pool that `LeagueTemplateImporter` harvests out of the
     shipped template. So for every such pool pair, EVERY `first + last`
     combination must satisfy guard 1 — "no real surname is in the pool" only
     rules out exact hits, and these names are composed at run time where no
     bundle scan can ever see them.
- Keep name-pool cultural diversity so rosters feel authentic in aggregate.

## 2. Biography jitter (deterministic, from the same per-player seed)

- **Age**: ±1 year, drawn so the league-wide jitter mean ≈ 0 (preserve age
  pyramid). `yearsPro` adjusted consistently (never negative, never > age−20).
- **College**: replaced with a different school of the same tier from a mapping
  table (P5 ↔ P5 of comparable football stature, G5 ↔ G5, FCS ↔ FCS). Never
  the real school; never the same fake school for two players who really
  attended the same school in the same class (avoid pattern reconstruction).
- **Draft origin**: year and round KEPT (drives contract/experience logic);
  pick fuzzed ±8 slots within the round (clamped to round bounds). Undrafted
  stays undrafted.
- **Body**: height ±1 in, weight ±2–4 % (position-plausible, re-clamped to the
  position's `PositionPhysicalProfile` range). At least one of the two must
  change for every player.
- **Hometown**: random (never the real one).

## 3. Careers — OVR arcs, never stat lines

- The shipped file contains, per player, per season: `{year, teamRef, ovr,
  role}` only — an **editorial ability estimate**, not the real production
  record. Derivation: real production percentile per season → OVR band →
  ±2 jitter.
- `PlayerSeasonHistory` rows are built from the arcs; displayable stat lines
  are **generated by the game's own stat model** from (ovr, position, role,
  era) with jitter — asserted to never reproduce a real season line exactly
  (QA gate checks headline stats: no generated season may match a real one on
  ≥3 of its headline categories simultaneously).
- Honors/awards abstracted: "league honors count" band (0 / some / decorated),
  never named awards with years.
- Injury history: only a coarse durability hint feeds generation; no real
  injury timeline ships.

## 4. Coaches

Same treatment: fictional names (same generator + guards), tenure `sinceYear`
±1, background (offense/defense) kept, **scheme identity kept** (fact — this
is what matters for gameplay), coaching-tree/lineage notes dropped.

## 5. What stays real (deliberately)

Team strengths and weaknesses, roster shapes and depth quality, league
structure, 2025 records (feeds `Team.lastSeasonWins`), 2026 pick ownership
(trade notes stripped of player names: "via trade" only), scheme identities,
aggregate age/experience distributions, positional group quality. This is the
realism the user experiences; none of it identifies an individual.

## 6. Pipeline & enforcement

1. Transform tool (build-time, in `tools/league-data/`): reads raw JSON +
   `globalSeed` → emits BOTH fixed templates (user requirement: two constant,
   always-launchable league sets — nothing regenerated per career):
   - `league_2026_publish.json` (publishProfile, bundled in every build);
   - `league_2026_dev.json` (devProfile: sound-alike names, real-ish team
     identities, exact careers — bundled in **DEBUG builds only**, excluded
     from Release via build configuration).
   Both carry final pre-solved attributes (fixed-seed derivation inside the
   tool) so a template launch is fully deterministic.
2. **Bundle gate** (release build phase / pre-ship script): scan the app
   bundle for (a) any string from the real-names blocklist, (b) any
   Levenshtein ≤ 2 variant of a blocklisted name, (c) the raw data filenames.
   Any hit fails the build. Plus a **source-level** check of every runtime
   name-pool pair (§1 guard 4) — a string scan cannot see a name the app
   composes at run time out of two arrays, and the pass verdict must state
   which surfaces it actually covers.
3. **QA gate** on the publish file: name guards (§1, recombination included),
   jitter coverage (every player ≥ 3 transformed fields), stat-line check (§3),
   no free-text `notes` payload, coach guards (§4 — `sinceYear` must actually
   have moved, not been clamped back onto the real value), pick-note scan for
   real player names.
4. **Recognizability spot-check** (manual, each regeneration): sample 20
   random players; a reviewer who knows the NFL must not be able to name the
   real counterpart from the in-app profile alone. Any confident hit → tighten
   the offending field's jitter and regenerate.
5. Raw data lives only in `tools/league-data/raw/` (repo-internal, never in
   any target's resources; add a comment header "DO NOT BUNDLE" + the bundle
   gate enforces it).

## 7. Residual risk statement

Even fully compliant, a "realistic 2026 league" is recognizable **in
aggregate** (a strong Detroit with an accurate veteran QB). Aggregate
resemblance to factual reality is the accepted, defensible position —
individual identifiability is not. Before an actual App Store release with
this content, have an IP lawyer review this spec and one generated build
(cheap relative to the risk; US market / NFLPA-OneTeam enforcement is real).
